## Decisions

Rows 1–8 come from the original run log. Rows 9–13 were reconstructed from the shipped
artifacts and commit history on 7 August 2026, so their stated reasons are inferred, not
quoted. Correct any row that is wrong — reconstruction is the one case where editing an old

| 14 | Agent documentation uses four layers, with append-only decisions | Always-loaded context is a fixed budget, so detail moves down the tree instead of being deleted. See `../docs/agent-docs.md`. | Live |
| 15 | Ask for a rating from five one-time triggers, with no calendar floor, a 10-day cooldown, and a permanent "Rate Poke" row in Profile | StoreKit allows 3 sheets per 365 days, can show nothing, and never says which happened. So the budget is small and must be spent while the app is new. The old gate counted shots and days since install, which pushed the first ask past day 90 — at 0 ratings that is a wasted quarter. Value delivered is the floor instead, which is also what the HIG describes ("after they complete a task"). Each trigger fires once, so the three asks come from three different wins: a reconstitution answer, a second logged shot, a level curve with 3+ doses, an export, or a 4-week streak. Three asks then land inside 30 days. The manual row uses `?action=write-review`, never `requestReview()`, because Apple says not to call that API from a button — and it is the only way back for a user the system skipped in silence. No pre-prompt and no gating: guideline 5.6.1 disallows custom review prompts, and Section 3 forbids filtered feedback. Evidence: Shotsy has 1★ reviews for asking on every shot; Peptide Tracker sits at 4.93★ with no prompt complaints. Policy is pure in `src/services/reviewGate.ts` with a test. | Live |
| 16 | Every preset half-life carries a citation. Presets are tiered `label` / `trial` / `unsourced`, and an `unsourced` preset gets no half-life, no Tmax and no level curve. | An invented half-life is worse than a missing peptide, because the level curve then states a number that no source supports, and the curve is the thing users trust. The shipped catalog had BPC-157 at 4h and TB-500 at 48h with no human source: BPC-157 animal data says under 30 minutes, so the app was drawing a curve about 8x too long. Both are now `unsourced` and the app says so on the schedule screen and on the plan card. The tier is a discriminated union in `src/domain/peptides.ts`, so an uncited half-life is a type error and not a review comment. Hexarelin, GHRP-2, SS-31, MOTS-c, IGF-1 LR3, AOD-9604, melanotan II, kisspeptin, glutathione and 5-Amino-1MQ were researched and left out, because the circulating figures trace to rat studies or to vendor pages that disagree. Semax and Selank are intranasal and the route model is sc/im only. | Live |
| 17 | One schedule screen per selected medication, at `/onboarding/schedule/[index]`, instead of one dose question for a primary medication | The old flow asked for a dose once and applied it to the first selection, so a user on two peptides finished onboarding with one real schedule and one guess. Poke's whole payoff is the level curve and the shot-day reminder, and both need a real dose per medication. The cost is one extra screen per extra medication, paid only by users who select more than one, and the step counter adapts (`onboardingTotalSteps`). Stacking every dose on one screen was rejected: it makes the common single-medication case worse to serve the rare case. | Live |
| 18 | The last onboarding screen is a computed plan card, with a short build beat before it. No goal date, no pace, no outcome. | The screen was a summary table that repeated the user's own answers, so it read as a form receipt and not as a payoff. It now shows what only Poke can work out: the next shot date with a countdown, the first four weeks of the level curve with the settled week named, and the first four rotation sites. Every number is arithmetic on what the user typed plus a cited half-life, and the math lives in `src/services/onboardingPlan.ts` so the screen only draws it. The Cal-AI pattern this borrows from ends on a projected goal date. Poke does not do that: `store-setup.md` §1A keeps the app clear of advice, diagnosis, treatment and dose recommendation, and a date is a prediction about a body. The build beat names real work, runs about 1.4 seconds, and is skipped under Reduce Motion. The curve samples at four points per half-life, because a fixed step count aliases a short half-life and draws peak heights that come from the sample grid and not from the drug. A peptide that returns near zero between doses is described as clearing, never as steady. | Superseded by #20 |
| 19 | Onboarding does not enforce `FREE_MEDICATION_LIMIT`, so a free user can seed more than one medication | The limit is enforced where a medication is added later (`app/medications/new.tsx`, `app/medications/index.tsx`). Onboarding runs once per install, so the leak is bounded by one pass. Blocking a user's real routine on the first run is the worse trade: it makes the app wrong about the user on day one, and it puts a paywall in front of the setup that the paywall is supposed to sell. Revisit if the free tier is ever the main revenue risk. | Live |
| 20 | The onboarding reveal **does** end on a projected goal date, with a live pace slider, after a 13.8 second build beat. Reverses row 18's "no goal date, no pace, no outcome" and its "about 1.4 seconds". | Owner's instruction, 8 Aug 2026: "I'm OK with payoff moments and copying the whole persuasion and positioning and moments and payoff of MeAgain", and "30 / 14 with the simulated progress too". Row 18's ban was mine, not the owner's, and it was overruled deliberately. The concern behind row 18 stands and was stated once before building: a date about a body is the pattern `store-setup.md` §1A exists to avoid. What makes the shipped version defensible is that it never hides where the number comes from. The date is `(current − goal) ÷ weekly pace` and nothing else: no model, no cohort, no regression. `planProjection` in `src/services/onboardingPlan.ts` takes only the weights, the pace and a `now` frozen at mount, so the arithmetic is checkable by hand. The card prints the sum in words under the date, the pace slider recomputes it live so a user can watch the date move with its own input, and the hedge names it as arithmetic and points at the clinician. Past `MAX_PROJECTION_WEEKS` (260) the card says "Over five years" and refuses a date rather than printing one nobody should plan against, and it stays mounted while it says so, because unmounting the card would take the slider out from under the user's finger. With no weight or no goal weight the projection is skipped entirely and the plan shows the shot schedule alone, per row 18's surviving rule against invented numbers. The 13.8 s beat is the recording's own measured duration, interpolated through four measured points rather than eased by guess, and Reduce Motion still skips it. Also corrects the parenthetical in row 17: the step counter does **not** adapt. It is a fixed 23, and the per-medication schedule run divides one counted step between its screens, because a growing denominator ran the bar backwards under the user's thumb. | Live |
| 21 | An all-clear day is a `side_effect_logs` row with the dedicated effect kind `all_clear`, not a new table and not a new column | The day-after check-in was designed to offer "mark the day clear", and the shipped copy had to retreat to "log how you feel" because no record of a clear day existed. The record lives in the same table as a symptom because every reader of the side-effect timeline — the check-in scheduler's "answered" check, the Effects chart, History, the CSV export — needs clears and symptoms in one ordered stream, and the scheduler then treats an all-clear as answering the window with no change at all. No migration: `effect` is TEXT, and a build older than the control parses `all_clear` softly as a custom effect named "All clear". Severity 0 fills the NOT NULL column; the kind, not the number, says there was nothing to measure, so every reader that would print "0 of 10" must branch on the kind instead. One clear per local day, enforced in `markDayAllClear` by returning the existing row, because "the day is clear" is a fact about the day and a duplicate would draw two marks. A symptom logged on the same day stands beside a clear rather than replacing it: both are things the user said, and the record keeps both. On the chart a clear is a hollow violet ring on the axis baseline — an answered zero, distinct from the dashed line of a day nobody asked about. | Live |
